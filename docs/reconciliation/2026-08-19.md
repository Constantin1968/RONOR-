## Human decision required before release

The current Telegram approval flow re-submits a request after human approval, while the runtime
does not yet expose an authenticated, replay-protected settlement protocol that can bind that
approval to the original decision. The MI9 core can validate prior approval metadata, but accepting
client-supplied metadata without a server-side trust mechanism would permit forgery.

Before a deployment or merge, choose and specify one protocol:

1. Approval authorises execution: runtime stores the pending decision server-side and exposes a
   scoped, one-time settlement endpoint with expiry and replay protection.
2. Approval authorises release only: runtime performs no external side effects before approval and
   releases an already-computed, immutable result after settlement.

This branch deliberately does not guess between those materially different semantics. Until the
protocol is selected, side-effecting missions that receive `allow-with-cosign` must not be
considered production-ready.
