## Approval settlement protocol

The selected protocol is now implemented without enabling it in production:

- Side-effecting missions are held before decomposition or worker execution.
- The runtime issues an opaque, cryptographically random approval identifier bound to the originating API key.
- `POST /api/runtime/approvals/:id/settle` accepts one authenticated approval or rejection.
- Settlement identifiers expire after 15 minutes by default, are capped at 60 minutes, and are
  deleted before an approved execution starts, preventing concurrent retry or later replay.
- A key mismatch is refused. Forged and already-consumed identifiers share the same opaque error.
- Telegram retains the local approval until runtime settlement succeeds. Read-only queries release
  their immutable held response; missions use the one-time runtime endpoint.

The pending registry is intentionally process-local. A runtime restart invalidates every outstanding
approval rather than risking a stale or duplicated execution. A future durable implementation must
preserve consume-before-execute and must not persist provider credentials or unredacted environment state.
